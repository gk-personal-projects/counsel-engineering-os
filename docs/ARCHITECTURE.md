# Counsel Engineering OS — Architecture

Status: T2.2 deliverable, governed by Gate T2-A ruling (2026-08-12, approved with amendments).

## 1 · The two-sided boundary (ruling A6 — designed now, not deferred)

Everything in this product belongs to exactly one side:

### REUSABLE RUNTIME (`runtime/`) — the PORTABLE CORE (0.1.5+)
Identical across every project that installs Counsel. Versioned as a unit. Written
harness-neutral (vocabulary contract: `runtime/HARNESS.md`) — the same skills, rules,
and agents run on Claude Code (first-class), Cursor, and Codex CLI. Harness-specific
mechanics (Claude hooks, model-alias map, plugin manifest; Cursor .mdc emission; Codex
config notes) live in `adapters/<harness>/`, thin by design.

- CTO orchestration doctrine (identity, staffing governor, synthesis contract)
- Reusable agents (tier-partitioned: core/ builder/ engineering/ full/)
- Reusable skills/procedures (grok, plan, debug, review, verify, adr, red-team, mentor,
  onboard, doctor, capabilities, recommend, checkpoint/restore/save-and-restart)
- Reusable rules (evidence, authority, orchestration, safety baseline, review governance,
  agent workflow, maturity)
- Capability logic (what the registries drive)
- Optional integrations (Superpowers detection/enhancement — never a dependency)
- Optional portable hooks (Core Continuity Hook Pack; advanced automation = Full OS)

Runtime files never contain: project names, stacks, hostnames, ports, paths, private
context, or per-project permission specifics.

### PROJECT CONTROL PLANE (installed into the target project from `scaffold/`)
Owned by the project. Never overwritten by updates without merge. Survives uninstall of
any capability.

- Project `AGENTS.md` constitution (instantiated from template + onboarding answers;
  harness-neutral, always-on rules embedded in an installer-managed sentinel region;
  on Claude Code a ~4-line `CLAUDE.md` shim imports it)
- `.claude/settings.json` permissions (Claude harness only; baseline + project entries)
- Project rules and path-scoped rules
- Project context (stack facts, commands, maturity, deployment/security constraints)
- ADRs / decisions ledger
- Per-project capability configuration (`.counsel/config.yaml` — which layers/capabilities
  are installed/enabled here)
- Session state (`.counsel/session/` — private, gitignore'd by default)

### Install mechanics across the boundary
The installer (`install-plan.ps1 -Harness claude|cursor|codex`) stages rules to the
harness-neutral `.counsel/rules/`, agents to `.claude/agents/` (Claude) or
`.counsel/agents/` (role cards elsewhere), skills to `.codex/skills/` / `.cursor/skills/`
where no plugin channel exists, assembles `AGENTS.md` with the sentinel rules region, and
instantiates control-plane templates. An ownership manifest
(`.counsel/manifest.json`: file → source version → hash) records every runtime-owned
file so that:

- **update** replaces only unmodified runtime-owned files (modified ⇒ 3-way prompt)
- **repair** restores runtime-owned files from the installed version
- **uninstall** removes only runtime-owned files; control-plane and app files untouched
- **doctor** detects drift between manifest and disk

The manifest is the boundary made mechanical. A future plugin package replaces the
"copy runtime files" half without touching the control-plane half — no redesign (A6).

## 2 · Composition model

```text
PUBLIC COUNSEL CORE (this repo)
  └─ ORGANIZATION / PERSONAL OVERLAY (optional, private; conventions, style capabilities)
       └─ PROJECT OVERLAY (control plane, generated by /counsel:onboard)
            └─ SESSION (private, checkpointed, recoverable)
```

Authority order (highest first): platform safety → user's live instructions → project
constitution → org/personal overlay → runtime rules → agent role → skill procedure →
defaults. Conflicts surface; lower layers yield.

One authoritative home per policy. Every restatement is a pointer, not a copy.

## 3 · Progressive layers

| Layer | Adds | Dormancy mechanism |
|---|---|---|
| Core | CTO doctrine, evidence law, safety baseline, onboard, doctor, mentor, grok, plan, native debug/review/verify, session continuity | — (always) |
| Builder | tech-lead, frontend, backend, test, debug specialists; git workflow; code review | tier dir not copied until installed |
| Engineering Team | principal-architect, principal-security, principal-data; ADR governance; two-agent review; performance | same |
| Full OS | red-team, reserve seats, advanced governance, advanced automation hooks | same |

Dormant = not present in the project's `.claude/` (zero context cost — the mechanism
proven by the reserve-pool pattern). Install/enable/disable/remove/upgrade are per
capability; removal never deletes decisions or project context. Full is never default.

## 4 · Staffing model (runtime doctrine)

L0 CTO-only → L1 single specialist → L2 feature team → L3 principal review (mandatory
for auth/session/tenancy/migration-class changes) → L4 full counsel + red-team
(mandatory before irreversible actions). Minimum sufficient organization; escalation
follows consequence and uncertainty, never keywords. Layers cap the available depth:
Core tops out at L1 advisory, Builder at L2, Engineering at L3, Full at L4.

## 5 · Memory & authority model

No agent holds authoritative project facts. Durable truth lives in the control plane:
ADRs/decisions ledger + project constitution. Session state is recoverable working
memory, never canon. Assistant auto-memory is treated as helpful, non-authoritative.

Durable **company memory** (strategist capability, 0.1.5) sits beside ADRs in the
control plane, in two explicit tiers: project memory (`memory/` in-repo, zero-config)
and an optional shared cross-project store linked via `.counsel/config.yaml`
`memory.shared_dir`. Governing law: `scaffold/memory/CONVENTIONS.md` (evidence tags,
append-at-anchor writes, scope routing). Auto-memory nodes become pointers into it.

## 6 · Session continuity (runtime capability, Core)

State files: RESTORE.md, STATE.json, DECISIONS.md, OPEN-ITEMS.md, ARTIFACT-REGISTRY.md,
SESSION-LOG.md (append-only), CHECKPOINTS/ (immutable). Semantic + mechanical
checkpoints. Recovery invariant: RESTORE vs STATE vs git vs filesystem — drift stops
work until reconciled.

**Core Continuity Hook Pack** (ruling A8, distinct class, available below Full OS):
- checkpoint/restore fully functional WITHOUT hooks
- hooks optional, gracefully degradable, doctor-validated before enablement
- no hidden Python / Git Bash / runtime / network / platform dependency
- documented command/file/failure behavior; failure never corrupts authoritative state
- crash recovery never relies on SessionEnd
- Advanced automation hooks are Full-OS explicit opt-in

## 7 · External posture (rulings A3/A4)

- **Agent Scaffold:** upstream/source only. Users never clone it. Derived material is
  marked and registered (PROVENANCE.md, NOTICE).
- **Superpowers:** optional integration. Core is complete without it; doctor verifies it
  *functionally* (its injection hook actually fires) before offering enhanced workflows;
  absence is never unhealthy.
- Historical Counsel artifacts: PRIVATE REFERENCE, never required at runtime or shipped
  (ruling A2/D-T2-003). Portable principles are re-expressed as ORIGINAL files.

## 8 · Registries (runtime, machine-readable)

`registry/capabilities.yaml` + `registry/dependencies.yaml`, schema-validated. They are
the single source driving doctor, recommend, install/enable/disable/remove, and
permission baseline generation. See registry/schema/.

## 9 · Distribution lifecycle

Scaffold-first: clone/download this repo → run installer against a target project.
v0.1.0-internal → v0.2.0-cofounder-alpha (Gate T2-M, HUMAN PUBLISH) → v0.5.0 public
beta → v1.0.0. Never published without an explicit publish ruling.
